1. AUTH CONTROLLER

A quoi il sert :
Le controleur Auth gere l'inscription et la connexion des utilisateurs.
Il permet de recuperer un token JWT pour acceder aux routes protegees.

Routes principales :
- POST /auth/register
- POST /auth/login

Cas d'utilisation :
- Creer un nouveau compte utilisateur
- Connecter un utilisateur existant
- Recuperer un token JWT pour tester les autres routes dans Swagger

Exemple login :
{
  "email": "seed.admin@logichain.fr",
  "password": "Password123"
}

Reponse attendue :
- 200 OK
- Un champ token
- Un objet user avec id, email, role, eventIds

Erreurs possibles :
- 401 : email ou mot de passe incorrect
- 409 : email deja utilise pendant un register
- 422 : donnees invalides, par exemple email mal forme ou mot de passe trop court


2. EVENT CONTROLLER

A quoi il sert :
Le controleur Event gere les evenements logistiques.
Un evenement represente le cadre principal du projet : festival, salon, rassemblement, etc.
Les zones, equipements, taches, anomalies et livraisons sont rattaches a un evenement.

Routes principales :
- GET /events
- POST /events
- GET /events/{eventId}
- PUT /events/{eventId}
- PATCH /events/{eventId}
- DELETE /events/{eventId}

Cas d'utilisation :
- Lister tous les evenements
- Creer un evenement avec des zones geographiques
- Modifier le statut d'un evenement
- Supprimer un evenement si on est admin

Exemple de test simple :
GET /events

Exemple eventId :
64a000000000000000000001

Exemple modification :
{
  "status": "active",
  "description": "Evenement demo modifie depuis Swagger"
}

Reponse attendue :
- 200 OK pour lecture/modification
- 201 Created pour creation
- 204 No Content pour suppression


3. ITEM CONTROLLER

Un item peut etre scanne, deplace, transfere a un responsable ou mis en maintenance.

- PATCH /items/{itemId}
- DELETE /items/{itemId}

Cas d'utilisation :

- Creer un equipement avec QR code
- Scanner un equipement sur le terrain
- Deplacer un equipement d'une zone vers une autre
- Changer le responsable d'un equipement
- Declarer une maintenance

Exemple lister les equipements :
GET /events/64a000000000000000000001/items

Exemple scan :
POST /items/64a000000000000000000201/scans
{

  "location": {
    "type": "Point",

  "details": {
    "source": "swagger-demo"
  }

10. SYNC CONTROLLER

A quoi il sert :
Le controleur Sync gere la synchronisation offline-first.
Il permet d'envoyer au serveur des operations faites hors ligne par un agent terrain.

Route principale :
- POST /sync

Cas d'utilisation :
- Synchroniser un scan fait hors connexion
- Synchroniser un mouvement d'equipement
- Detecter un conflit de version
- Eviter d'ecraser une modification plus recente

Principe :
Chaque equipement possede un offlineVersion.
Le client envoie expectedOfflineVersion.
Si la version correspond, l'operation est appliquee.
Sinon, l'API renvoie 409 Conflict.

Exemple scan offline :
POST /sync
{
  "operations": [
    {
      "clientOperationId": "op-swagger-001",
      "itemId": "64a000000000000000000201",
      "expectedOfflineVersion": 1,
      "action": "scanned",
      "actorId": "64a000000000000000000103",
      "payload": {
        "source": "offline-device-1",
        "location": {
          "type": "Point",
          "coordinates": [2.3522, 48.8566]
        }
      }
    }
  ]
}

Reponse attendue :
- 200 OK si l'operation est appliquee
- 409 Conflict si la version offline n'est plus la bonne

COMMENT FONCTIONNE L'ARCHITECTURE : CONTROLLER, SERVICE, REPOSITORY, MODEL

L'idee simple :
Quand tu fais un test dans Swagger, la requete ne va pas directement dans MongoDB.
Elle traverse plusieurs couches. Chaque couche a un role precis.

Ordre de passage :
Swagger
-> Route
-> Controller
-> Service
-> Repository
-> Model Mongoose
-> MongoDB


1. ROUTE

A quoi ca sert :
La route indique quelle fonction appeler selon l'URL et la methode HTTP.

Exemple :
GET /api/v1/events/64a000000000000000000001/items

Dans le code :
src/routes/api.routes.ts

La route dit :
"Quand quelqu'un appelle GET /events/:eventId/items, il faut appeler items.list"

Exemple dans le projet :
this.router.get("/events/:eventId/items", asyncHandler(items.list));


2. CONTROLLER

A quoi ca sert :
Le controller recoit la requete HTTP.
Il recupere les parametres, le body JSON, puis appelle le service.

Il ne doit pas contenir toute la logique metier.
Son role est surtout de faire le lien entre HTTP et le reste du code.

Exemple :
src/controllers/item.controller.ts

Pour lister les equipements :
public list = async (request, response) => {
  response.status(200).json(await this.items.list(request.params.eventId));
};

Traduction simple :
Le controller recupere eventId dans l'URL.
Il appelle ItemService.list(eventId).
Puis il renvoie le resultat en JSON avec le code HTTP 200.


3. SERVICE

A quoi ca sert :
Le service contient la logique metier.
C'est ici qu'on applique les regles importantes du projet.

Exemples de logique metier :
- verifier qu'un id est valide
- dire quoi faire quand un item est introuvable
- changer le statut d'un equipement apres un scan
- ajouter une ligne dans l'historique
- gerer les conflits offline

Exemple :
src/services/item.service.ts

Quand on scanne un equipement :
public async scan(id, data) {
  return this.addHistory(id, { status: ItemStatus.InTransit }, "scanned", data);
}

Traduction simple :
Quand un item est scanne, le service decide que son statut devient in_transit.
Il ajoute aussi une action "scanned" dans l'historique.


4. REPOSITORY

A quoi ca sert :
Le repository est la couche qui parle avec MongoDB.
Il contient les requetes vers la base.

Le service ne fait pas directement ItemModel.find().
Il passe par le repository.

Pourquoi ?
Parce que ca evite de mettre des requetes MongoDB partout dans le projet.
Si on veut modifier une requete, on sait ou aller.

Exemple :
src/repositories/item.repository.ts

Le repository peut faire :
- findByEvent(eventId)
- findById(id)
- updateById(id, data)
- deleteById(id)
- appendHistory(id, update, history)

Traduction simple :
Le repository est le "specialiste base de donnees" pour une ressource.


5. MODEL

A quoi ca sert :
Le model Mongoose decrit la structure des donnees dans MongoDB.
Il dit quels champs existent, quels champs sont obligatoires, quels types sont attendus, et quels index utiliser.

Exemple :
src/models/item.model.ts

Un equipement contient par exemple :
- eventId
- qrCode
- label
- category
- status
- zoneCode
- responsibleUserId
- carbonKg
- history
- offlineVersion

Le model sert aussi a definir les index :
Par exemple un index sur eventId + status + zoneCode pour rechercher rapidement les equipements d'un evenement selon leur statut et leur zone.


6. MONGODB

A quoi ca sert :
MongoDB est la vraie base de donnees.
C'est la que les documents sont stockes.

Les collections principales sont :
- users
- events
- items
- tasks
- deliveries
- anomalies
- notifications
- monitoringmetrics


EXEMPLE COMPLET : LISTER LES EQUIPEMENTS D'UN EVENEMENT

Dans Swagger, tu fais :
GET /events/64a000000000000000000001/items

Voici ce qui se passe :

1. Swagger envoie la requete HTTP.

2. La route reconnait :
GET /events/:eventId/items
et appelle ItemController.list.

3. Le controller recupere :
eventId = 64a000000000000000000001
et appelle ItemService.list(eventId).

4. Le service verifie que eventId est un ObjectId MongoDB valide.
Si l'id est invalide, il renvoie une erreur 400.

5. Le service appelle ItemRepository.findByEvent(eventId).

6. Le repository utilise ItemModel pour faire une requete MongoDB.

7. MongoDB renvoie les equipements de cet evenement.

8. Le controller renvoie la reponse au client avec :
200 OK
et la liste des equipements en JSON.


EXEMPLE COMPLET : SCANNER UN EQUIPEMENT

Dans Swagger, tu fais :
POST /items/64a000000000000000000201/scans

Body :
{
  "actorId": "64a000000000000000000103",
  "location": {
    "type": "Point",
    "coordinates": [2.3522, 48.8566]
  },
  "details": {
    "source": "swagger-demo"
  }
}

Voici ce qui se passe :

1. La route appelle ItemController.scan.

2. Le controller valide le body avec Zod.
Si le body est mauvais, l'API renvoie 422.

3. Le controller appelle ItemService.scan.

4. Le service decide la regle metier :
un scan passe l'equipement en status in_transit.

5. Le service ajoute une entree dans l'historique :
action = scanned
actorId = l'agent
location = coordonnees GPS

6. Le service appelle le repository pour mettre a jour l'item.

7. Le repository utilise le model Mongoose ItemModel.

8. MongoDB modifie le document dans la collection items.

9. L'API renvoie l'equipement mis a jour.


RESUME TRES SIMPLE

Route :
Elle choisit quel controller appeler selon l'URL.

Controller :
Il recoit la requete HTTP et renvoie la reponse.

Service :
Il contient les regles metier.
C'est le cerveau fonctionnel.

Repository :
Il fait les requetes vers la base.
C'est le pont vers MongoDB.

Model :
Il definit la forme des documents MongoDB.
C'est le plan des donnees.

MongoDB :
C'est l'endroit ou les donnees sont stockees.


PHRASE SIMPLE A DIRE A L'ORAL

"Quand une requete arrive depuis Swagger, elle passe d'abord par une route.
La route appelle un controller.
Le controller recupere les donnees de la requete et appelle un service.
Le service applique la logique metier.
Ensuite, il appelle un repository pour acceder a MongoDB.
Le repository utilise un model Mongoose, qui definit la structure des donnees.
Enfin, MongoDB renvoie les donnees, et le controller les renvoie au client en JSON."
