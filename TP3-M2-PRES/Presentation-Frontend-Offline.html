Texte pour l’oral

LogiChain est une application mobile pour suivre le matériel, les tâches et les livraisons. Son mode hors ligne permet de garder les actions sur le téléphone et de les envoyer plus tard.

Pour passer à la suite

Le point de départ est une difficulté fréquente sur le terrain.

02 / Le projet

Pourquoi cette application ?

Sur le terrain, la connexion peut se couper.

Le travail continue

Un agent doit pouvoir scanner un équipement ou mettre à jour une tâche.

Les actions doivent rester

Il ne doit pas avoir à tout recommencer au retour du réseau.

Texte pour l’oral

Sur le terrain, la connexion peut se couper. L’application garde donc les informations et les actions sur le téléphone pour permettre au travail de continuer.

Pour passer à la suite

Ce besoin se traduit par quatre objectifs.

03 / Le projet

Les objectifs de l’application

L’application aide l’utilisateur à travailler, même sans réseau.

Consulter

Voir les informations déjà chargées.

Agir

Scanner et enregistrer des modifications sans réseau.

Reprendre

Envoyer les actions quand le réseau revient.

Comprendre

Savoir si une action est en attente ou s’il y a un problème.

Texte pour l’oral

L’application a quatre objectifs : rendre les données accessibles, enregistrer les actions, les envoyer plus tard et afficher les problèmes éventuels.

05 / Les choix techniques

Les outils utilisés et pourquoi

Chaque outil répond à un besoin.

React Native et TypeScript

Pour créer les écrans mobiles et mieux vérifier le code.

SQLite

Pour garder les données et les actions sur le téléphone.

NetInfo et AppState

Pour savoir si le réseau est disponible et si l’application est active.

Pour le scan : Vision Camera. Pour la session : Keychain. Pour la carte : SVG.
Texte pour l’oral

React Native sert à construire les écrans mobiles. SQLite garde les données sur le téléphone. NetInfo détecte le réseau et AppState indique si l’application est active.

Pour passer à la suite

Ces outils doivent répondre à des besoins simples pour l’utilisateur.

Texte pour l’oral

L’application doit rester réactive et garder les actions. Une connexion lente ne doit pas bloquer le scan suivant, et les actions en attente doivent rester visibles.

08 / Le fonctionnement hors ligne

Ce que l’application garde sur le téléphone

SQLite garde deux choses séparément.

Les informations

Les équipements, les tâches et les autres données téléchargées.

Les actions à envoyer

Les scans et les modifications qui attendent une confirmation.

Dans le code, les deux tables s’appellent records et operations.
Texte pour l’oral

SQLite garde les informations téléchargées et les actions à envoyer dans deux tables séparées. À la réouverture, l’application retrouve les deux.

Pour passer à la suite

Ces données permettent de garder plusieurs fonctions disponibles sans réseau.

09 / Le fonctionnement hors ligne

Ce que l’application permet sans réseau

Avec des données chargées à l’avance, le travail peut continuer.

Consulter

Voir les équipements, les tâches, les livraisons et les zones.

Enregistrer

Scanner un équipement ou modifier une tâche.

Signaler

Texte pour l’oral

Sans réseau, l’application permet de consulter les données déjà chargées et d’enregistrer des actions. Un signalement demande aussi une position GPS valide.

Pour passer à la suite

En plus des données, le téléphone garde les actions qui restent à envoyer.

10 / Le fonctionnement hors ligne

Les actions en attente

Une liste garde les actions enregistrées avant leur envoi.

Une action est ajoutée

Un scan ou une modification est conservé dans SQLite.

Elle reste sur le téléphone

L’application la retrouve après fermeture et réouverture.

Elle attend une confirmation

Elle quitte la liste lorsque son envoi est accepté.

Texte pour l’oral

Cette liste est parfois appelée une file d’attente. Elle garde les actions séparément des données téléchargées. Une action enregistrée sur le téléphone attend encore sa confirmation par le serveur.

Pour passer à la suite

Voici comment une action entre dans cette liste.

11 / Le fonctionnement hors ligne

Comment l’application enregistre une action

Exemple : une tâche est marquée comme terminée.

1. Elle vérifie

L’application vérifie les informations nécessaires.

2. Elle enregistre

Elle garde la modification dans SQLite.

3. Elle affiche

Elle montre la modification et la place en attente d’envoi.

Texte pour l’oral

Quand une tâche est terminée, l’application vérifie les informations puis enregistre la modification. Elle peut ensuite l’afficher. Si l’enregistrement échoue, elle affiche une erreur.

Pour passer à la suite

Une fois l’action enregistrée, l’écran peut être mis à jour.

12 / Le fonctionnement hors ligne

Ce que l’utilisateur voit tout de suite

Il voit sa modification sans attendre l’envoi.

Avant

La tâche n’est pas terminée.

Après la modification

Elle apparaît comme terminée sur le téléphone.

En attendant

La modification reste à envoyer pour être confirmée.

Les signalements restent dans la liste des actions à envoyer jusqu’à leur envoi.
Texte pour l’oral

Une tâche terminée hors ligne apparaît tout de suite comme terminée. Cet affichage est dit optimiste : la modification est montrée avant sa confirmation. Si elle est refusée, l’affichage est corrigé.

Pour passer à la suite

La modification est visible sur le téléphone, mais elle doit encore être envoyée.

13 / Le fonctionnement hors ligne

Ce qui se passe quand le réseau revient

L’application reprend les actions en attente.

Elle détecte le réseau

L’envoi automatique reprend si l’application est active.

Elle envoie les actions

Elle les transmet les unes après les autres.

Elle met à jour les données

Les actions confirmées quittent la liste d’attente.

Il faut garder l’application active pour cette reprise automatique.
Texte pour l’oral

Quand le réseau revient et que l’application est active, les actions sont envoyées. C’est la synchronisation. Le bouton Synchroniser maintenant permet aussi de lancer cet envoi.

Pour passer à la suite

L’envoi ne réussit pas toujours au premier essai.

14 / Le fonctionnement hors ligne

Si l’envoi ne se passe pas comme prévu

L’application indique ce qui se passe.

L’envoi réussit

L’action est confirmée et retirée de la liste.

Le réseau coupe

L’action reste en attente pour un prochain essai.

L’action pose problème

L’écran indique un refus ou un conflit à résoudre.

Texte pour l’oral

Une action confirmée quitte la liste d’attente. Si le réseau coupe, elle reste sur le téléphone. Un refus ou un conflit est affiché pour que l’utilisateur puisse agir.

Pour passer à la suite

Parmi ces problèmes, un conflit demande un choix de l’utilisateur.

15 / Le fonctionnement hors ligne

Si deux personnes modifient la même chose

Exemple : deux personnes changent le même équipement.

Garder la version serveur

L’application retire la modification locale et garde la version reçue.

Réappliquer la modification

L’application prépare un nouvel envoi de la modification.

Texte pour l’oral

Un conflit peut arriver quand deux personnes modifient le même équipement. L’application propose de garder la version du serveur ou de réappliquer la modification locale. Le nouvel envoi doit encore être accepté.

Pour passer à la suite

Ce fonctionnement se retrouve dans une fonction importante sur le terrain : le scan.

16 / Les fonctions de l’application

Comment fonctionne le scan

L’application reconnaît les équipements déjà chargés sur le téléphone.

La caméra lit le code

La caméra lit le QR code ou le code-barres.

L’application cherche

Elle retrouve l’équipement dans les données chargées.

Le scan est gardé

L’action est enregistrée, puis le téléphone donne un retour.

Le même code est ignoré pendant 1,5 seconde pour éviter une répétition immédiate.
Texte pour l’oral

La caméra lit le code et l’application cherche l’équipement dans ses données. Le scan est ensuite enregistré sans réseau. Si le code est inconnu ou ambigu, un message l’indique.

Pour passer à la suite
